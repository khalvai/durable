Durable
Workflow Engine

Fault-tolerant execution of long-running, multi-step business processes — with durable state, crash recovery, retries, and saga compensation.

TypeScript Node.js SQLite · WAL Fastify 25 tests
Working vertical slice · npm run dev · ./scripts/demo.sh
This project asks a simple question: what happens when a multi-step backend process crashes halfway through? The engine is a durable state machine that makes progress survive process death, retries safely, and rolls back completed work when a later step cannot succeed.

The core challenge Execute side effects exactly once in effect, while tolerating at-least-once delivery and arbitrary crashes.
Every step here touches an external system and has a real side effect. A crash can happen before the call, after the call, or while waiting for the response. The hard part is not making the happy path work — it is making every failure point safe.
03 · Design goals

Three guarantees

Durability

Every state transition is committed to SQLite before the next action starts.

write-ahead state

Recovery

A crashed worker's lease expires. Another worker reclaims the step and resumes from the last checkpoint.

leases + fencing

Idempotency

Every step gets a stable key. Re-executing a failed step returns the original result instead of repeating the effect.

effectively once
at-least-once execution + idempotent effects = effectively-once outcome
These three guarantees reinforce each other. Durability lets us recover; leases let another worker take over; idempotency makes the retry safe.
04 · Concept 1 — Idempotency

Repeat without
repeating the effect

Idempotency means repeating an operation has the same effect as doing it once. The engine can only promise at-least-once execution; a stable key lets each downstream service collapse retries into one result.

workflow-service.ts · stable key per step
const steps = workflow.steps.map((step, index) => ({
  id: randomUUID(),
  index,
  name: step.name,
  idempotencyKey: `${runId}:${index}:${step.name}`,
  retry: resolveRetryPolicy(workflow, step),
}));
// compensation reuses the key with ":compensate"
services.ts · replay returns the first result
const existing = this.charges.get(request.idempotencyKey);
if (existing) {
  return { paymentId: existing.paymentId, amount: existing.amount };
}
// otherwise: charge once, then store under the same key
Attempt 1Charge succeeds; the worker crashes before saving the step result.
Attempt 2The retry sends the same key and receives the original pay_1.
Effectively onceOne side effect, despite two execution attempts.
The engine guarantees at-least-once execution. It cannot make an external HTTP call exactly-once. Instead, every step gets a stable key built from the run id, step index, and step name. Handlers pass that key downstream. The payment service checks its map first, so a replay returns the original payment instead of charging again. Compensation uses the same key with a ":compensate" suffix, so undo operations are idempotent too.
05 · Concept 2 — Saga

Saga: undo completed
work in reverse

A saga replaces one distributed transaction with a sequence of local transactions. When a step fails permanently, the engine compensates the steps that already succeeded — newest first.

1
Reserve inventory✓ succeeded
→
2

3

↩Release inventorycompensated
↩Refund paymentcompensated
—No compensationfailed step
executed right-to-left
Only completed steps are compensated. Steps after the failure are marked skipped. Compensation itself is retried and idempotent.
store.ts · beginCompensation()
SELECT id, step_index FROM steps
 WHERE run_id = ?
   AND step_index < ?
   AND status = 'succeeded'
 ORDER BY step_index DESC;
This is the saga pattern. There is no distributed transaction across the warehouse, payment, and shipping services. Instead, every completed step has a compensating action. A permanent failure marks later steps skipped, selects the succeeded steps with ORDER BY step_index DESC, and queues them for compensation. The claim query also waits until no later step is still pending, so undo really runs newest-first.
06 · Concept 3 — Step

A step is the durable
unit of work

A step has a name, an execute function that performs a side effect, an optional compensate function, and its own retry and timeout policy. Its state is persisted, so it can be retried or undone after a crash.

types.ts · StepDefinition
export interface StepDefinition<Input, Output> {
  name: string;
  execute(ctx: StepContext<Input>): Promise<Output>;
  compensate?(ctx: StepContext<Input>, output: Output): Promise<void>;
  retry?: Partial<RetryPolicy>;
  timeoutMs?: number;
}
executePerforms the real side effect and receives the stable idempotency key.
compensateUndoes the effect if a later step fails. Retried with a :compensate key.
retry / timeoutPersisted on the step, so in-flight runs keep their policy.

A step is the durable unit of work. It is not just a function call: it has a persisted status, attempt counters, a lease, a retry policy, an output, and an optional compensation. The engine claims it, records the attempt, executes the side effect, then persists the result with a fenced update. A crash between execute and persist is safe because the retry uses the same idempotency key.

The engine holds no workflow state in memory. Kill it at any point and another worker can continue.
The API and the engine share only the database. That is what makes the system recoverable: there is no hidden in-memory state to lose. The store is isolated behind a small interface, so a Postgres adapter can replace SQLite without changing the engine.

09 · State machine

Run lifecycle

queued active terminal · success rollback terminal · needs attention
A run moves forward one step at a time. A permanent step failure switches the run into compensation mode; completed steps are undone in reverse. If a compensation itself fails permanently, the run ends in failed and needs operator attention. Cancellation stops future work but is not a rollback.

Leases are the failure detector. A worker that dies stops renewing its lease. When the lease expires, any worker can reclaim the step. We mark the interrupted attempt as lease_expired, then retry with the same key.
11 · Consistency

Zombie workers can't
overwrite newer state

fenced completion
UPDATE steps
   SET status = 'succeeded',
       output_json = ?
 WHERE id = ?
   AND status = 'running'
   AND lease_owner = ?
   AND attempts = ?;

-- 0 rows updated → discard result
1

Worker A's lease expires while it is still executing.

2

Worker B reclaims the step and completes it.

3

Worker A finally returns — and tries to save its result.

4

The guard matches zero rows, so A's stale result is discarded.

The fencing token is the pair (lease_owner, attempts). A result is only accepted from the worker that still owns the current attempt.
Leases alone are not enough. A paused worker can wake up after its lease expired. Every completion is conditional on still owning the lease and still being on the same attempt number. This is a classic fencing-token pattern.

16 · Engineering judgment

Trade-offs & next steps

Deliberate for this slice

Scope choices

  • SQLite — zero-ops durability; one writer at a time.
  • In-memory adapters — demo services reset on restart.
  • Version recorded, not enforced — definition evolution is future work.
  • Cancellation ≠ rollback — stops work, does not undo it.
Roadmap

Where it goes next

  • Postgres adapter + Docker Compose.
  • Metrics & dashboard for run health.
  • Dead-letter queue and manual retry for failed runs.
  • Parallel fan-out, child workflows, delayed steps.
The interesting part is not the happy path — it is the explicit treatment of every crash window.
I want to be honest about scope. SQLite and in-memory adapters are appropriate for a verification project, not for production scale. The important architectural boundary is the store interface and the stateless engine; those are what a production version would build on.
